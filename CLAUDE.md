# CLAUDE.md

## Proyecto

SPA en React 18 + Vite que muestra el precio horario de la luz (PVPC) en España. Los precios se descargan de la API de REE/ESIOS con un workflow programado y se publican como JSON estáticos junto a la web; el navegador no llama a ESIOS. Toda la UI y los nombres de funciones/variables están en español; mantener esa convención. La documentación (este fichero, README, comentarios, mensajes de commit y PR) se escribe siempre en español.

## Comandos

```bash
npm install
npm run dev       # servidor de desarrollo Vite
npm run build     # build de producción en ./dist
npm run preview   # sirve el build localmente
npm run lint      # ESLint sobre src/ con --max-warnings 0 (cualquier warning hace fallar el lint)
npm run datos     # descarga los precios que falten a public/datos (requiere la variable ESIOS_API_KEY)
npm run datos:resumen  # solo regenera public/datos/resumen.json (sin API key)
```

No hay tests ni framework de testing configurado.

Versiones principales: Vite 8 (requiere Node 20.19+ o 22.12+; CI usa Node 24), React 18.3 (se probó React 19: funciona, pero añade ~79 kB al bundle sin aportar nada que se use), Tailwind 4 (con `@tailwindcss/vite`, sin PostCSS ni `tailwind.config.js`; requiere Safari 16.4+, Chrome 111+ o Firefox 128+), date-fns 4. ESLint usa configuración plana en `eslint.config.js`; está en ESLint 9 porque `eslint-plugin-react` aún no admite ESLint 10. `react-hooks` 7 incluye las reglas del React Compiler (p. ej. `set-state-in-effect`).

Las mejoras pensadas para más adelante están en `IDEAS.md`.

## Despliegue

`.github/workflows/deploy.yml` construye y publica `dist/` en GitHub Pages. Por eso `vite.config.js` fija `base: "/precio-luz/"`; no quitarlo o se rompen las rutas de los assets en Pages.

El workflow se dispara con cada push a `main`, a mano (`workflow_dispatch`) y de forma programada (cron en UTC: cada 30 min de 18:20 a 20:50, que cubre de ~20:20 a ~22:50 en verano y de 19:20 a 21:50 en invierno, más una repesca a las 6:30). En cada ejecución:
1. `npm run datos` descarga de ESIOS los días nuevos con el secret `ESIOS_API_KEY`. En un push, si falla, se despliega igualmente (`continue-on-error`).
2. Si hay cambios en `public/datos`, los commitea como `github-actions[bot]` («Precios actualizados») y hace push. Ese push, hecho con `GITHUB_TOKEN`, no dispara otro workflow, así que el despliegue ocurre en la misma ejecución.
3. Construye y despliega; las ejecuciones programadas solo lo hacen si hubo precios nuevos.

`concurrency` impide dos ejecuciones a la vez. GitHub desactiva los workflows programados tras 60 días sin actividad en el repositorio.

## Arquitectura

`src/App.jsx` concentra el estado y la carga de datos; `scripts/actualizar-datos.js` (Node; usa `StringToNumerLocale`, `horaReloj`, `periodoPeaje` e `INICIO_2_0TD` de `src/utils.js`, y por tanto `date-fns`) descarga y normaliza los precios; `src/utils.js` contiene helpers puros (formato, fechas, periodos, niveles); `src/datos.js`, `pedirMes` (la petición del fichero de un mes, compartida por la vista de día y el mapa de calor); `src/useAncho.js`, el hook con el ancho real de un contenedor (`ResizeObserver`); `src/components/` tiene las piezas visuales: `Controles` (fecha con botones de día anterior/siguiente limitados al rango permitido, zona, unidad; exporta también `Segmentado`, el grupo de botones de opción reutilizable), `SelectorDuracion`, `FranjaHoras` (las 24 barras, protagonista de la página), `TablaHoras` (detalle desplegable), `FichaPotencia` (término de potencia, desplegable al final de la vista de día), `CalculadoraFactura` (debajo; usa `medias.json`) e `Historico` (vista de histórico, #9; lee `datos/resumen.json`; muestra el gráfico de evolución, el mapa de calor, una tabla por año con los cambios regulatorios intercalados y la sección «Antes de comparar»). `GraficoEvolucion` es SVG a mano (sin librería) dibujado al ancho real del contenedor (`useAncho`) para que el texto no se escale: línea del precio medio, banda de la hora más barata a la más cara, cambios regulatorios arriba (nombre corto `corto` de `HITOS`, en dos filas si se pisan; la excepción ibérica como zona sombreada) y línea vertical con el detalle al pasar el ratón o con ← → Inicio Fin. Con «Desde 2014» cada punto es un mes (medias de los días); con «Último año» y «90 días», un día. El eje Y empieza en 0 o en el precio más bajo si es negativo. `MapaCalor` (en el histórico, «Todas las horas de un año») es un `<canvas>` con un día por columna y una hora del reloj por fila, de un año o de los últimos 365 días; no usa `resumen.json` sino los ficheros de cada mes (`pedirMes`, con su propia caché de promesas). Dos modos de color por tramos: «Frente a la media del día» (divergente azul-rojo: no se usan el verde y el rojo de los niveles porque con daltonismo rojo-verde no se distinguen) y «Precio» (secuencial de casi blanco a la tinta); los extremos de la escala se recortan a los percentiles 2 y 98. Las dos 02:00 de otoño se promedian y la de primavera queda vacía (`horaReloj`). Ratón, toque y teclado (flechas, Re Pág/Av Pág, Inicio, Fin; Intro abre el día) eligen una casilla; «Ver el día» usa `enlaceDia`/`verDia` de `App.jsx`, que cambian a la vista de día con esa fecha (`pushState`). `src/hitos.js` guarda esos cambios regulatorios (`HITOS`: fecha, `hasta` y `tituloFin` si fue temporal, explicación y norma en el BOE); `CAMBIOS` y `cambiosEntre(desde, hasta)` dan los días en que cambia la definición del precio, para marcarlos en el histórico y avisar en las comparativas.

Hay dos vistas, `dia` e `historico`, sin router: el parámetro `vista` de la URL decide cuál se pinta en `main`. Los enlaces de la cabecera son `<a href>` de verdad (se pueden abrir en otra pestaña) y el clic normal cambia de vista sin recargar. Cambiar de vista hace `pushState` (para que «Atrás» funcione, con un listener de `popstate` que vuelve a leer la URL); el resto de cambios, `replaceState`. `Historico` se carga con `React.lazy` en su propio chunk para no engordar la vista de día. Zona y unidad son comunes a las dos vistas; en el histórico `Controles` se usa sin `onFecha` y oculta el selector de día. El estado y las cargas de la vista de día siguen en `App.jsx` aunque se esté en el histórico (el día ya cargado no se pierde al volver).

Flujo de datos:
1. Vista, fecha, zona, unidad y duración se leen de la URL (`?vista=historico&fecha=YYYY-MM-DD&zona=cym&unidad=mwh&duracion=2`) y se reescriben con `history.replaceState` (`pushState` si cambia la vista); los valores por defecto (vista de día, hoy, PCB, kWh, sin duración) no aparecen en la URL.
2. Las peticiones pasan por `cargarDia(fecha)`, una caché en memoria de promesas por día: solo guarda los aciertos (un fallo se borra para poder reintentar, p. ej. mañana antes de publicarse). Tras cargar un día se precargan el anterior y el siguiente. Mientras carga otro día se sigue mostrando el anterior (`datos` guarda `{ fecha, data }`); solo se atenúa si la carga tarda más de 150 ms, y el esqueleto de carga aparece únicamente en la primera carga. Las respuestas de un día que ya no es el elegido se descartan (`vigente`).
3. Datos: `scripts/actualizar-datos.js` llama a `https://api.esios.ree.es/archives/70/download_json?date=YYYY-MM-DD` (API key en la cabecera `x-api-key`, leída de `ESIOS_API_KEY`) y normaliza `data.PVPC` a `{ Hora: "HH:00", PCB, CYM }`. Los precios llegan como strings con formato español (`"123,45"`) y se convierten con `StringToNumerLocale`. Algunos días antiguos traen solo `GEN` en lugar de `PCB`/`CYM`, de ahí el fallback. Para días sin publicar (p. ej. mañana antes de ~20:15, hora a la que Red Eléctrica publica el PVPC del día siguiente) la API responde **HTTP 200** con `{"message": "No values for specified archive"}`. Se guarda en `public/datos/AAAA/MM.json` (`{ "AAAA-MM-DD": [...] }`, un día por línea para que los diffs sean pequeños); Vite lo copia tal cual a `dist/datos/`. Sin `--desde`, empieza en el día siguiente al último guardado, así que un hueco en medio no se vuelve a pedir solo. El primer día con datos en ESIOS es el 01/04/2014 (`FECHA_MINIMA`, en la web y en el script). Al final de cada ejecución (o solo eso, con `--solo-resumen`) se regenera entero `public/datos/resumen.json`, para el histórico (#9): `dias` (por fecha, `[media, mín, máx, horaMín, horaMáx]` de PCB seguido de lo mismo para CYM) y `perfiles` (por mes y zona, precio medio de cada hora del reloj). En los días de 25 horas la API numera las horas seguidas de `00:00` a `24:00` (las posiciones 2 y 3 son las dos 02:00), mientras que en los de 23 horas ya se salta `02:00`; `horaReloj` lo traduce. `leerMeses` solo recorre carpetas de año para no tropezar con `resumen.json`. A la vez se escribe `public/datos/medias.json` (~7 KB), con lo que necesita la vista de día sin descargar el resumen entero: `{ "AAAA-MM": [mediaPCB, mediaCYM, puntaPCB, llanoPCB, vallePCB, puntaCYM, llanoCYM, valleCYM, baratasPCB, baratasCYM] }`. Las medias por periodo (de las horas de cada periodo de peaje del mes) y `baratas` (media de las 3 horas seguidas más baratas de cada día, `mediaHorasBaratas`) solo existen desde junio de 2021; antes, el array tiene dos valores.

`src/comparativas.js`: `pedirMedias()` (una petición, olvidada si falla) y `compararConHabitual(medias, fecha, zona, mediaDia)`, que compara la media del día con la del mismo mes en hasta 3 años anteriores, solo con los años posteriores al último cambio regulatorio (`CAMBIOS`); si no hay ninguno, usa los 3 anteriores y devuelve el `cambio` para avisar. Por debajo de un 5 % de diferencia se considera «lo habitual». `App.jsx` lo muestra bajo los datos del día (`fraseHabitual`; a partir del doble se expresa en «veces»). La media de un día es la misma en PCB y CYM: las zonas solo se diferencian en el reparto entre horas. `perfilAnio(perfiles, anio, zona)` (también en `comparativas.js`) da el perfil horario medio de un año, cada hora relativa a la media del día, y sus horas más barata y más cara; lo usan `PerfilesAnuales` (gráficos pequeños de 2019, 2022 y el año actual con la misma escala; se probó una rampa de tres tonos en un solo gráfico, pero no se distinguían bien sobre el fondo `papel`) y la tabla «Año a año». El histórico abre con cuatro cifras destacadas (`cifrasDestacadas`: día más caro y más barato por media, hora más cara y días con alguna hora negativa) y tiene también `MismoMes`: barras con la media de un mes elegido en cada año, con una línea vertical entre dos años si hubo un cambio regulatorio entre medias (`cambiosEntre`).
4. En la web, `pedirDatos(fecha)` lee el día del fichero de su mes (`pedirMes`, con `cache: "no-cache"` para revalidar con el servidor; Pages cachea 10 min). Los meses se guardan como promesas en `meses`; si el día no está en el fichero se olvida el mes, para volver a pedirlo (mañana se publica más tarde en el mismo mes), y se lanza `SinDatos`. Un mes sin fichero (404 en Pages; en `vite dev`/`preview` llega `index.html` con 200, por eso se mira el `content-type`) cuenta como vacío. `estado` (`cargando`, `ok`, `sin-datos` o `error`) no se guarda: se deriva de `resultado`, la última carga terminada, comparando su fecha e intento con los actuales. Así el efecto no llama a `setState` de forma síncrona, que la regla `react-hooks/set-state-in-effect` prohíbe.
5. Mientras se ve el día de hoy, un segundo efecto comprueba (también vía `cargarDia`) si ya hay precios de mañana en los ficheros; si no, vuelve a mirar a las 20:15 y luego cada 10 minutos (los datos llegan cuando el workflow programado los publica, unos minutos después que en ESIOS). Cuando los hay, aparece el botón «Ver los precios de mañana».
6. Atajos de teclado globales en `App.jsx` (← / → cambian de día, H vuelve a hoy), solo en la vista de día y limitados al mismo rango que el selector. Se ignoran con modificadores o si el foco está en un campo de formulario, porque allí las flechas ya tienen función (fecha, botones de opción). La pista de atajos del pie solo se muestra con puntero fino (variante `pointer-fine:`).
7. Los precios de la API vienen en €/MWh; para kWh se dividen entre 1000. `formatearPrecio` usa 3 decimales en el resumen y 5 en el detalle para kWh (2 para MWh).

Fechas: usar siempre los helpers de `utils.js` (`hoy`, `manana`, `parseISO` de date-fns). `new Date("YYYY-MM-DD")` y `toISOString()` trabajan en UTC y desplazan el día.

Los días de cambio de hora tienen 23 o 25 horas: no asumir 24 elementos (por eso las listas usan el índice como `key` y la franja calcula sus columnas con `precios.length`).

**Término de potencia** (`src/potencia.js`): `POTENCIA` guarda por año, en €/kW y año, los peajes (resolución anual de la CNMC), los cargos (orden anual del Ministerio, «segmento tarifario 1» = 2.0TD según el art. 3.2 del RD 148/2021) y el margen de comercialización del PVPC (3,113, solo en P1: Orden ETU/1948/2016, prorrogada sin fecha por la Orden TED/1484/2021). **Hay que añadir el año nuevo cada enero**; mientras tanto `potenciaDe(anio)` devuelve el último disponible. No viene de ESIOS: el archivo 70 solo trae el término de energía. Comprobación de las cifras en la issue #1.

**Factura** (`src/factura.js`, `estimarFactura`): suma día a día potencia (P1 y P2 por separado; el IVA reducido dependía de la mayor), energía (consumo de punta, llano y valle, como viene en la factura, cada uno × el precio medio de ese periodo en el mes, de `medias.json`), financiación del bono social (€/año por suministro), impuesto eléctrico (5,11269632 % con mínimo de 1 €/MWh; su base es la del IVA de un suministro eléctrico, así que incluye el bono social pero no el contador), alquiler del contador (0,81 €/mes) e IVA sobre todo lo anterior. Impuestos y bono social son tramos con fecha `desde`: en 2026 hubo rebajas temporales (RDL 7/2026, del 22/03 al 31/05: impuesto eléctrico al 0,5 % e IVA al 10 % con menos de 10 kW). **Cuando el Gobierno cambie un tipo o la orden del bono social, hay que añadir el tramo.** La calculadora solo ofrece meses del año en curso (los valores de potencia son de ese año). Tiene dos modos: «Cuando toca» (cada periodo a su precio medio) y «En las horas baratas»: el consumo de los aparatos programables marcados (`APARATOS_PROGRAMABLES`: lavadora 6,45 %, lavavajillas 3,4 %, secadora 1,53 %, horno 5,79 % y termo eléctrico 5,9 % del consumo eléctrico medio de los hogares, IDAE SPAHOUSEC III con datos de 2021, calculado desde su tabla «Consumo por uso y zona climática») sale de los tres periodos a partes proporcionales y se valora al precio de las horas baratas; se muestra el ahorro frente al primer modo.

Conceptos de dominio:
- **Zona**: `PCB` = Península, Canarias y Baleares; `CYM` = Ceuta y Melilla.
- **Periodos de peaje** (`periodoPeaje`): valle/llano/punta según hora, día de la semana (fin de semana = todo valle), festivos y zona; CYM tiene un reparto de horas distinto. `esFestivo` da los festivos en los que todo el día es valle: según la Circular 3/2020 de la CNMC, solo los nacionales de fecha fija y no sustituibles (1/1, 6/1, 1/5, 15/8, 12/10, 1/11, 6/12, 8/12 y 25/12; ni Viernes Santo ni los lunes que pasan a festivo cuando uno cae en domingo), así que no hay que actualizarlos cada año. Solo existen desde la tarifa 2.0TD (`INICIO_2_0TD`, 01/06/2021): antes `periodoPeaje` devuelve `null` y `hayPeriodos(fecha)` es falso, así que `FranjaHoras` no pinta la banda de periodos y `TablaHoras` oculta la columna.
- **Nivel de precio** (`nivelesPrecio`): divide el rango min–max del día en tercios (bajo/medio/alto); colorea las barras.
- **Tramo más barato** (`tramoMasBarato`): parte de la hora más barata y se extiende mientras las horas vecinas no superen el mínimo + 15 % del rango del día; es el titular de la página. El umbral se eligió comparando con datos reales (resultados estables entre 10 % y 20 %).
- **Mejor bloque** (`mejorBloque`): para la duración elegida en el selector (1, 2, 3, 4, 6 u 8 h), las horas seguidas con menor precio medio; en empate, el primero. Se marca con un corchete sobre las barras. No cruza la medianoche.
- **El precio no es homogéneo en el tiempo** (ver `src/hitos.js`): hasta el 31/05/2021 es la tarifa 2.0A (sin periodos; `PCB` = `CYM`), desde el 01/06/2021 la 2.0TD; del 15/06/2022 al 31/12/2023 incluye el coste de la excepción ibérica; desde 2024 se indexa en parte a futuros (25/40/55 %). Siempre sin impuestos y en euros corrientes.
- Puede haber **precios negativos** (p. ej. 12/10/2026); las barras los recortan a 0.

## PWA

`vite-plugin-pwa` (configurado en `vite.config.js`) genera el manifiesto, el service worker (Workbox, `registerType: "autoUpdate"`) y lo registra solo. Estrategias de caché:
- Recursos de la app: precacheados en cada build.
- Ficheros de precios (`/precio-luz/datos/`): `NetworkFirst` (red con 5 s de espera; la copia guardada solo se usa sin conexión). No entran en el precache (Workbox solo precachea js, css y html por defecto).
- Google Fonts: `StaleWhileRevalidate` para el CSS y `CacheFirst` para las fuentes.

El service worker no se activa con `npm run dev`; para probarlo: `npm run build && npx vite preview`. Los iconos (`public/pwa-*.png`, `maskable-512x512.png`, `apple-touch-icon.png`) se generaron a partir del rayo de `favicon.svg`; la versión *maskable* tiene fondo completo y el rayo dentro de la zona segura.

## Diseño

Tokens en el bloque `@theme` de `src/index.css` (variables CSS `--color-*` y `--font-*`, que generan las clases): colores `papel`, `tinta`, `suave`, `linea` y `barato`/`medio`/`caro` (solo para el nivel de precio; cada uno con una variante `-intenso`, más oscura, para la barra seleccionada); tipografías Barlow (`font-sans`) y Barlow Semi Condensed (`font-display`, cifras y titulares), cargadas desde Google Fonts en `index.html`. No hay librería de componentes: todo es Tailwind sobre HTML semántico. En Tailwind 4 `leading-*` prevalece sobre el interlineado que trae `text-*` (también con variantes responsive como `sm:text-6xl`); los colores de los SVG (`GraficoEvolucion`) repiten los valores del `@theme` como constantes.
